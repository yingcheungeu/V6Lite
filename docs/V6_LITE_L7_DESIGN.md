## 2. 订单合同与持久化身份（2.2-1）

每个已托管持仓至多认领**一张**有效 GTC `STP LMT` `SELL` 保护单；`outsideRth=False`，`account` 与合格股票 `conId` 必须精确匹配。`orderRef` 使用发送前已持久化的独立 `v6l-...` 保护 intent id，关联 `position_id`；存储原始 `orderId`、`permId`、`clientId`、合约、触发价、限价、申请数量、已成交数量、当前服务器剩余量、最后确认时间和修改世代。不能以相同 symbol 单独认领，不能把旧的 TP/STOP intent 复用为保护身份。程序重启后 `permId` 与 `orderRef` 必须一起核对；`orderId` 还需结合 client 身份。重复匹配或字段矛盾即状态不明，不新挂同类单。

触发价采用**持久化**的 `positions.stop`；TP1 完成后采用持久化的 `breakeven_stop`，见 `store.py:99-115,905-915`。John 已定 `protect_limit_offset_pct=3%`，即 `0.03`；SELL 限价 = 触发价 × `0.97`，按该合约真实最小价格增量**向下**取整，要求 `0 < 限价 < 触发价`。最小增量与合约/交易所可接受性必须在 Paper 核实；若不可取得或改单被拒，保持原单、P0 告警，不用未经验证的两位小数代替。该参数进入配置校验和指纹，live 批准不能在参数变更后沿用。本项不改变入场止损/止盈的 ATR 倍数。

`STP LMT` 触发后只转成限价卖出意图，**不能保证成交**；`outsideRth=False` 也不能被表述为盘后保护。GTC 的真实跨日存续、公司行动后的处理、Paper/Live 账户及该股票/交易所支持情况均以 Paper 与 IBKR 界面核实为准。本机 `ib_insync` 仅提供字段与调用接口。

## 3. 超卖不变式与卖出单状态机（2.2-2、2.2-3）

对每个股票定义：`P` = 最新**完整、可核验**的券商持仓股数；`S` = 该保护单仍可成交的最大剩余量；`T` = 所有自有 DAY TP 卖单最大剩余量；`X` = 外部/手工/组合单可能卖出的最大剩余量；`U=max(0,P-S-T-X)` 是未被卖单覆盖的股数。核心不变式为 `S+T+X ≤ P`。查询失败、`remaining` 缺失、改/撤请求未确认、UNKNOWN 或跨日执行记录不完整时，取**可能的最大未成交量**而不是把空查询当 0；证据不足就不发任何增加卖量的订单。股票必须按合约 ID/账户精确归属，未知侧别算 SELL；不可解析组合单阻断本股票/必要时全账户。现有 `_reserve` 已把外部及未知侧别的工作单纳入预留（`engine.py:1687-1706`），L7 不得绕过。

**只减不增：** 新鲜券商 `P < S+T+X` 时，马上请求减小或取消本系统可控保护单，使自有可卖量下降；同时阻断所有新增卖单和新开仓，P0 报出超额。减量请求未确认期间仍按旧的最大 `S` 计算，不假设已安全。更严格地说，若差异由外部新卖单在满额保护单之后插入，违规可能已经在检测前发生；本系统无法阻止另一个 TWS/client 在两次查询之间下单。因此“任何时刻所有在途卖单”只有在**独占账户订单写权限、操作员不另行提交 SELL**，或 broker 原生原子协调得到证实时才可被证明。发现外部卖单立即冻结本 symbol/入场、减小本系统卖单并 P0；不能把事后修复写成从未超卖。人工紧急卖出须先通过 TWS 确认本系统卖单减量/撤销，再提交人工单。独占前提无法落实则 Live 为 NO-GO。

唯一允许自动**增加**保护单剩余量或补挂的条件：同一账户/合约的新鲜完整 `reqPositions`、所有 client 的工作单及足够覆盖有关意图的成交记录一致，且重复查询/事件处理后稳定，`P` 与账本的已解释数量一致，所有未知订单已认领或人工处置。现有 `executions_today()` 只在请求中限定 `clientId` 与账户（`broker/ibkr.py:678-702`）；函数名不能证明跨日或其他 client 的历史已完整。L7 须提供更完整的 broker 证据/明确的不可用状态。凡无法取得完整证据，只允许减量或维持原单，不允许补挂或加量，P0 报未保护股数。不能把 `IB.placeOrder()` 的同步返回当改单确认：需收到服务器回执，并以新鲜工作单字段与执行/持仓复核该 `permId` 的**实际剩余量及价格**。改单被拒或超时视为 UNKNOWN，数量预留按旧/新请求的较大可能值计算，禁止下一笔 TP。

### 3.1 各中间状态的最坏卖量

下表用 3 股已成交持仓、TP1 目标 1 股作例子；`S/T/X` 表示**尚可能成交**的最大剩余量。每笔成交 `f` 同时使 `P` 和相应订单剩余量减 `f`，所以只要没有外部独立新增卖单，等式保持。表中“确认”指经 broker 证据确认，而非本地 `PendingSubmit/PendingCancel`。

| 状态/事件 | P | S | T | 最坏 `S+T` | 处理与失败/重启分支 |
|---|---:|---:|---:|---:|---|
| 入场成交前 | 0 | 0 | 0 | 0 | 不提交裸卖单。parent/child 候选须 Paper 证明激活规则。 |
| 首股 BUY 已成交、保护尚未确认 | 1 | 0 或 UNKNOWN 1 | 0 | ≤1 | **未保护空窗**，P0/阻断新入场；崩溃重启先认领而不重复发单。Live 阻断见 §1。 |
| 保护首股已确认 | 1 | 1 | 0 | 1 | 若再有部分 BUY 成交，先增加实际持仓，新增 1 股暂未保护；只在三证据一致后把 S 加至 2。 |
| 全部 3 股保护已确认 | 3 | 3 | 0 | 3 | 常态；保护触发但未成交仍记 S=3。 |
| 为 TP1 申请把 S 从 3 改成 2，尚未确认 | 3 | 最坏 3 | 0 | 3 | **不得发 TP**；修改失败/重启按 S=3 寻回，不能假定已改成 2。 |
| S=2 由券商确认，TP 尚未发 | 3 | 2 | 0 | 2 | 有 1 股临时无保护；TP 不发/被拒则取三证据后补回，期间 P0 若保护缺口持续或已触止损。 |
| TP1 提交中/UNKNOWN | 3 | 2 | 最坏 1 | 3 | 意图先落库；发送结果不明仍预留 1，**不再增 S**；重启按身份查询，禁止重复 TP。 |
| TP1 与保护同时工作 | 3 | 2 | 1 | 3 | 任一方部分成交 `f`：`P` 和其未成交量同减 `f`；总量始终≤新 P。 |
| TP1 全部成交 | 2 | 2 | 0 | 2 | TP1 账本结算后按实际持仓修改**同一**保护单到保本触发价；若价位改单未知，数量仍按 2 预留并 P0。 |
| 保护先成交 2 股，TP1 仍工作 | 1 | 0 | 1 | 1 | 保留 TP 至证据确认/必要时撤单；不能另发程序化 STOP。若 STOP 与 TP 同时成交，最多卖 3 股。 |
| TP 撤单请求已发、尚未确认 | 3 | 2 | 最坏 1 | 3 | 不补保护数量；撤单后迟到成交仍能让两端剩余量同步下降。 |
| TP 撤单已确认且成交核实为 0 | 3 | 2 | 0 | 2 | 三证据一致后才可把 S 改回 3；若 TP 已部分成交，以实际 P 为上限。 |
| 保护被取消/拒绝/到期 | 3 | 0 | 0 | 0 | 3 股未保护，P0 + 阻断新风险；仅在三证据完整后补挂，否则人工处理。 |
| 触发跳空、限价未成交 | 3 | 3 | 0 | 3 | 仍有 3 股价格风险；P0，人工检查与决定，不自动改市价/加另一个 STOP。 |
| 正常关机，DAY TP 撤单未确认 | 3 | 2 | 最坏 1 | 3 | 保留已确认 GTC；重启先认领两单，TP 结算不明不能把 S 加至 3。 |
| 正常关机，DAY TP 撤单已确认 | 3 | 2 | 0 | 2 | 关机前或下次启动三证据一致后补足 S；做不到则关机卡片/P0 报 1 股未保护。 |
| 外部 SELL 1 股在 S=3 时被另行提交 | 3 | 3 | 0，`X=1` | **4 > 3** | 绝对不变式已被外部并发破坏；立即冻结/P0并减 S 至 2，但必须承认检测前无法补救。 |

对于实际数量 `P` 与 TP 目标 `q`，先确认 `S≤P-q-T-X`，再发送 `q`；此时最坏总卖量 `S+T+X+q≤P`。所有保护/TP 的部分成交只是同时从持仓与该订单剩余量扣除同一成交数量，因此不会让左边超过右边。条件是外部不能另外开新卖单、券商改单确认准确、成交与订单清单完整；这些条件尚未通过 Paper 证明。不要把 OCA 净额相抵计算，所有订单都按原始最大剩余量相加。

### 3.2 OCA 的位置及与旧方案的差异

旧重设计 §8.4 提过 OCA 数量协调。`ib_insync.IB.oneCancelsAll()` 仅填充两个字段（见 §1）；本地资料不能证明 IBKR 在**不等量**保护单/TP、TP 部分成交、跨 client 重启后的比例减量和 overfill-protection 行为。首版设计**不依赖 OCA 保证不超卖**，而以“保护先减且确认、TP 后发”的毛数量不变式为核心。是否额外设同组 OCA 仅作二道防线，必须先在 Paper 验证完整/部分成交后：保护是否被取消、是否按股数正确减量、是否短时无保护、订单块保护是否真的禁止同时成交。未经 Claude 批准与 John Paper 证实，不把 OCA 作为默认开关或容量扣减依据；这是对旧 §8.4 中 OCA 协调措辞的**明确待裁决修订**，并非声称已满足原设计。

## 4. 各事件与运行控制（2.2-4）

1. **ENTRY 部分成交：**每一批经 execution 确认的 BUY 增加 `P`；立即请求覆盖实际持有股数。原 ENTRY BUY 尚可继续成交，保护确认前的 `U` 必须显式 P0/阻断新开仓；若保护已触发/成交，先请求撤掉尚在途的 BUY，迟到 BUY 仍按新敞口重新入账和保护，绝不把零仓/已关闭账本当作不会再买。parent/child 的替代见 §1。
2. **TP1 保本：**仅在 TP1 实际成交与阶段终态核实后，用同一保护单 `orderId`/`permId` 修改 `auxPrice` 到持久化保本价，限价随之重算；数量不另增。改价 UNKNOWN 时保留原单可能的卖量，P0 报“保本保护价未确认”，不能提交第二个 STOP。
3. **STOP 路径（2.2-6）：**程序化 STOP 改为“监控该 GTC 单的状态、触发与价格风险 + 告警”，不得再 `_send` 一张额外的 DAY STOP 卖单；若保护缺失则 P0/人工介入，不能用现有重试路径自行补发裸 STOP。引擎检测价格越过止损并不等于券商单已触发或成交。
4. **正常停机：**停新开仓、逐个撤销自有 DAY ENTRY/TP 并核实成交/撤单；**已确认且数量正确的 GTC 保护单保留**。撤单状态 UNKNOWN 时不补保护增量，关机报告列 P/T/U、订单 ID 和核实状态；不能为“干净关机”撤掉最后的保护。当前 `shutdown()` 会取消全部自有单（`engine.py:2009-2051`），第十五批必须改。
5. **重启/断线恢复：**禁止 TP 与新开仓；取得 fresh position、全 client 工作单、可覆盖相关订单的 execution，先按 `orderRef+permId+account+conId` 认领原 GTC，再复核类型、GTC、价格、数量；之后认领 DAY/UNKNOWN、对账、计算最坏预留，才恢复 TP。无法改写其他 client 所建订单时，不新挂替代单；P0 交给操作员在 TWS 处理并重新核验。空的本地 `openTrades()` 或订单列表不证明 GTC 已消失。
6. **冻结、kill、日损：**kill/日损/冻结继续阻止新增风险，**不能自动撤掉已确认保护**。若 `P<S+T+X`，先安全减量；若身份/状态不明，不执行“补挂”或新 TP，P0 卡片列持仓、保护剩余、其他 SELL、未保护股数与订单号。解冻仅凭可核对的 broker 证据，不凭本地状态按钮。
7. **拒单、意外撤单、GTC 取消：**收到 `Inactive`/`Cancelled`/拒单回调或在完整查询里发现缺失，立即停新开仓、P0，计算可确认的 `U`；消息写明可能由公司行动、期限或人工操作导致，但**不推断原因**。先排除 UNKNOWN/其他 client/延迟查询，再三证据一致时才补挂；否则手工处理。每日开盘前与收盘后逐持仓核验 GTC 的账户、身份、数量、价位及是否仍可成交。
8. **成交更正/迟到成交：**`execId` 修订、撤单后成交或跨日缺失记录使数量无法闭合时，保守计原订单最大可能剩余量，阻断加量/TP，并 P0；只在完整新证据证明 `P` 更小时减小保护单。账本修订沿用既有异常/审计机制，不用“Cancelled”字符串当终态。

## 5. 触发但未成交的识别和 P0（2.2-5）

监控新鲜工作单和状态事件：一旦保护单出现服务端“已触发”证据（具体字段/状态须 Paper 核实），仍有 `remaining>0`，且新鲜盘口/成交价已低于可卖的限价，判定“触发未成交”；若 broker 不提供可靠触发标记，价格越过触发价但未有可确认 execution 时先发**“疑似触发/保护状态不明”P0**，不得声称已经触发。断线或没有新鲜报价时也不能把沉默解释为安全。重复通知节流，但 P0 状态持续显示直到 broker 证据或人工记录解除。

P0 卡片必须显示 `symbol`、账户脱敏标识、持仓 `P`、保护单 `orderRef/orderId/permId`、触发价、限价、订单状态/剩余 `S`、其他 SELL `T/X`、未保护或未成交股数、证据时间及不确定性，并给编号步骤：① 在 TWS 核对真实持仓、保护单和成交；② 立即停止/避免新增卖单，必要时先协调现有单；③ 由 John 判断人工操作并记录结果；④ 恢复前重新对账。**程序不会自动改市价单、自动追价或另发独立 STOP。** 本方案的损失可能超过止损价与 3% 限价差，包括盘后跳空。

## 6. John 必须在 G3 Paper 实测（2.2-7）

| 场景 | 必须留存的可核对证据与通过条件 |
|---|---|
| 强行结束进程 | 进程消失后 TWS 仍显示相同 `permId/orderRef` 的 GTC STP LMT，数量/价位正确；重启只认领、不重复发单。特别抓部分 ENTRY 成交至保护确认窗口。 |
| 断开本机网络 | 网络断开期间券商端 GTC 状态、实际触发/成交及恢复后的执行记录；未知则 P0，不补挂。 |
| Gateway 重启 | 本地连接/回调断开后 GTC 是否仍在；新会话能否以相同 client 修改、跨 client 是否只可查询；不能改时阻断。 |
| TP 部分成交与撤单竞态 | 先减保护单，再发 TP；逐事件截图/导出 `P,S,T,X`，每一刻 `S+T+X≤P`，撤单迟到成交与保护部分成交也要覆盖。 |
| 止损触发但限价未成交 | 制造可控 Paper 跳空/限价不可成交情形；确认触发识别、P0 卡片、没有自动市价或追价。 |
| 盘后至次日开盘 | `outsideRth=False` 的 GTC 是否仍工作，次日公司行动/重连后价量是否仍正确；盘外风险如实显示。 |
| 入场部分成交与 parent/child 备选 | 记录 BUY 部分成交到 GTC 被券商确认的每个时间点；另测 bracket child 的激活时机/数量、强退时状态。若无法证明持续保护，Live 保持 NO-GO。 |
| GTC 被取消/改单被拒/外部卖单 | 验证 P0 和未保护股数、只减不增、未知状态不重复挂单；外部单产生的瞬时超卖不可被事后检测“洗白”。 |

真实 Paper 验证必须由 John 主动启动并留订单/成交/界面证据；本设计及 FakeBroker 不连接 Gateway。

## 8. 本设计等待的裁决

1. Claude/John 对“减量确认后发 TP、OCA 仅为待验证的附加措施”相对旧 §8.4 的修订表态；若坚持 OCA，先用 Paper 证明不等量部分成交和按比例减量，且仍用毛卖量断言。
2. 对入场 fill→保护确认及 TP 减保护→TP 接单的两个空窗，选择经 Paper 证实的 broker 原生原子机制，或由 John 明确裁决是否接受有量化、可报警的短暂未保护敞口；若硬性要求全程全额保护，则未解决前 L7 不满足 Live 前置条件。
3. 确认同账户无其他独立卖单写入者的操作约束；若允许并发 TWS/其他 bot 下 SELL，需要额外 broker 原生原子防护并验证，客户端轮询无法保证绝对不变式。

上述三项未裁定并通过 Paper 证据时，不能把第十五批设计或本地测试报告写成 Live 准入通过。
