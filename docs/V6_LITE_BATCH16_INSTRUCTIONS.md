### F1（P0）自有卖单的成交，被当作“迟到或外部卖单”处理

**复现**
1. **止损正常全部成交**（20 股保护单一次成交）：
   - 发出 P0“托管标的出现外部卖单”；
   - 还对已经成交的 GTC 发出了一次撤单。
   每一次正常止损都会产生一条错误的 P0。
2. **止损部分成交，且工作单快照超过 5 秒**（例如成交回报恰好在扫描或历史数据请求期间到达）：
   - 20 股的保护单成交 5 股，引擎随即**撤掉剩下 15 股的保护单**；
   - 止损已经触发、正在成交的时候，剩下 15 股失去了券商端保护。
3. **TP1 全部成交，且快照超过 5 秒**：
   - 6 股 TP 成交后，剩余 14 股的 GTC 被整张撤掉。

**原因**
- `_protection_on_sell_fill` 把所有自有卖单的成交都当作“迟到卖单”处理；
- 保护单自身成交时，`confirmed_remaining`／`pending_max_remaining` 没有同步减少，于是被误判成 `S > P`；
- 快照过期的分支在判断“是否需要减量”之前，就整张撤掉 GTC。

**修复**
- **a. 保护单自身成交**：在入账的同一事务里，把 S（`confirmed_remaining`、`pending_max_remaining`，以及 pending 的剩余）按成交量同步减少。
  - P 和 S 同时减少，不变式自动保持，**不做任何券商写操作，也不发“外部卖单”告警**。
  - 全部成交后状态改为 FILLED，不发撤单。
  - 发一张正常的“止损已成交”卡片，级别按现有退出成交卡片，写明成交股数、均价和剩余持仓。
- **b. 自有 TP 成交**：P 和 T 同时减少，S 不变，不变式保持，不需要动保护单。只有当 TP 已被撤销、保护已恢复之后又来了迟到成交（此时 `S > P − T`），才需要减 S。
- **c. 需要减 S 时，只用账本里能确定的数量计算**：
  - P 来自账本；
  - T 取自有在途 TP 的最大剩余量；
  - 自有成交不会让 X 增加。
  所以不依赖 5 秒内的工作单快照。用同 ID 改单，把 S 减到 `P − T`；只有目标为 0、并且这张单不是正在成交的保护单本身时，才撤单。**删除“快照过期就整张撤 GTC”的分支。**
- **d. 测试**：
  - 三个复现场景，每个都分快照新鲜、快照过期两种情况；
  - 保护单部分成交，以及全部成交；
  - 断言：撤单 0 次；“外部卖单”告警 0 次；除迟到成交的情形外，改单 0 次；每一步都满足 `S+T+X ≤ P`。

### F2（P1）非末股 TP 被拒或没有发出时，保护不会恢复

**复现**：TP1（20 股中的 6 股）提交时被券商拒绝。GTC 停在 14 股，60 秒后仍是 14 股，只有 P0。裁决要求恢复到实际持仓。

**原因**
- `TP_NEEDS_RESTORE` 只处理末股（旧 GTC 已不存在）的情形；
- `_protection_send_tp` 的三条 P0 路径（没有报价、报价过期、限价不能立即成交）都把状态留在 `WORKING`，`tp_stage` 不清空。结果保护永远不恢复，新入场也一直被阻断。

**修复**
- TP **确定没有发出**（被拒、没有报价、报价过期、限价不能立即成交）时，进入 `TP_NEEDS_RESTORE`：
  - 保护单仍在：取得三证据后，用同 ID 改单加回到实际持仓。这属于“有证据的增加”，允许；
  - B 空窗在恢复获得确认时结束，记 `[PROTECT_GAP] kind=B outcome=tp_not_sent`。
- TP 结果不明（`maybe_sent`）：维持现在的处理，不恢复，发 P0。
- **测试**：上面四种“没有发出”的情形，都在 30 秒内恢复到 P；结果不明的情形不加量。

### F3（P1）IB API 没有 `Triggered` 这个订单状态

ib_insync／TWS API 的订单状态只有以下几种：
- `PendingSubmit`、`PendingCancel`、`PreSubmitted`、`Submitted`
- `ApiCancelled`、`Cancelled`、`Filled`、`Inactive`

STP LMT 触发之后，状态仍然报 `Submitted`。因此 `trigger unfilled` 这张 P0 只有 FakeBroker 能触发，实盘中永远不会发出。另一方面，`trigger suspected` 在每次现价 ≤ 触发价时都发 P0，即使止损正在正常成交。

**修复（不依赖状态名）**
- 保护单剩余 > 0，且现价 ≤ 触发价：发 **P1“价格已到止损价，券商保护单应在执行”**。每次穿越只发一次。
- 出现以下任一情况，发 **P0“止损触发但限价未成交”**：
  - 现价 < 限价；
  - 现价 ≤ 触发价持续 `protection.trigger_unfilled_p0_seconds` 秒（新参数，默认 60），并且保护单剩余量没有减少。
- FakeBroker 删掉 `Triggered` 状态，测试改用真实的状态集合。
- G3 运行手册里加一条：触发时，记录 TWS 中该单的显示和 API 状态。

### F4（P1）稳态下每轮都做三项查询，且一次超时就发 P0

**复现**
- 有一个持仓时，10 轮 tick 里 `open_orders`、`positions_fresh`、`executions_today` 各调用了 10 次。主循环约 1 秒一轮，每个持仓每秒发 3 个请求。
- `open_orders` 只超时一次，就发了 P0“保护单三项证据不完整”。

**修复**
- **稳态**（`WORKING`，没有 pending、没有 `tp_stage`、没有空窗在计时）：三证据每 `protection.steady_check_seconds` 秒查一次（默认 15）。**有流程在进行时**（A/B 空窗、改单待确认、TP、恢复），每轮都查。
- 稳态下单次查询失败：只记日志，下一轮重试；连续失败超过 `protection.evidence_fail_p0_seconds` 秒（默认 60）才发 P0。流程进行中的查询失败，维持现在的 P0。
- 两个新参数和 F3 的参数都纳入指纹，并写进示例配置。
- F1 修好后，成交处理不再依赖 5 秒内的快照，降低稳态查询频率是安全的。请在报告中逐条确认，没有其他代码路径依赖 `_working_at` 的新鲜度。
